# Universal Style Doctrine

This doctrine is normative unless a project explicitly declares a different local policy. Language guides may sharpen it; they must not translate it back into conventional defaults.

Code is a machine-facing semantic artifact, maintained by agents whose capability rises over time. Spend cognition lavishly in service of the task. Do not stop at the first familiar or adequate move; search for the strongest construction the problem admits. Difficulty carries no tax; slack does. Optimize for semantic precision, mechanical analyzability, canonical structure, runtime efficiency, and semantic density per token. Human accessibility in the classic onboarding sense is not a design objective. Write for successors more capable than yourself.

Design must be intentional rather than accreted. Keep a top-down shape that exposes the system’s ontology and causal structure. Refactor early and aggressively. Delete dead paths, compatibility husks, redundant abstractions, ceremonial wrappers, tutorial scaffolding, and contingent glue. Comments should carry irreducible rationale, proof obligations, or external facts. If a feature remains patched-on rather than native to the design, reshape the system.

Command the full language without apology. Its sharpest features, metaprogramming, type-level machinery, and code generation are ordinary means of expression. Overload operators to state domain algebra directly. Familiarity, pedagogy, and median-reader accessibility have no veto.

Make illegal states unrepresentable inside the trusted core. At boundaries, refine input into lawful domain values rather than carrying ambiguity inward. Let the domain model carry the system’s states, transitions, capabilities, effects, and failures. Boundary refinement may fail; lawful internal transformations should be total. Types are executable architecture: proof, representation, and optimization surface.

Model algebraically. A good module is a small calculus: precise vocabulary, explicit states and effects, lawful transformations, and composable interfaces. Seek the strongest abstraction the problem admits. Mathematical structure compresses laws and exposes exact handles to tools. Treat cost as semantics: choose representations and algorithms by the actual machine, and reject surface simplicity purchased with hidden work.

Store each truth once and derive every projection. Abstract a real invariant as soon as it is visible; literal repetition is not a prerequisite. Concentrate sophistication behind lean, exact semantic surfaces; cold machinery may be as dense and generative as the design demands.

Rectify names: within a project, one nontrivial noun means one thing, and each domain concept has one canonical name. Keep names compact, precise, and domain-faithful. Use mathematical or Unicode notation directly when it minimizes semantic distance and the toolchain carries it exactly. Keep call sites small and direct; qualification must earn its keep.

Fail hard unless recovery is real. Validate and refine at boundaries; do not preserve doomed control paths with dummy defaults, nullable theater, catch-and-limp wrappers, or error laundering. An irrecoverable contradiction terminates loudly. Recovery is explicit, typed domain behavior, never ambient politeness.

Exploit libraries and dependencies aggressively when they supply stronger machinery than local ownership would. NIH has no virtue, but imported semantics remain part of the machine; choose on whole-system merit. Backward compatibility, shims, and parallel old/new paths exist only under a live contract.

Tooling posture is strict. Formatting, linting, type checking, dependency pruning, and semantic verification are part of the build contract. Any law exact machinery can enforce must cease to be prose. Exploit compilers, analyzers, and transformation tools at full strength. Write code for exact transformation first and human reading only incidentally.
